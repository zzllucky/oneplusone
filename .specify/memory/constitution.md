# 1+1=2 Constitution

> 项目：1+1=2（工作目录 `D:\oneplusone`）
> 定位：面向**初中学生**的中考英语单词记忆 Web 网站 —— 账号体系、每日背词目标、先学习后测验、
> 选择题测验、错题本与错题专项练习（首个功能：`specs/001-word-study-quiz`）。
> 主要用户为未成年人，涉及未成年人个人信息，适用下方"领域合规"条款。

## Core Principles

### I. 库优先（模块自包含）

每个功能必须首先作为一个独立、自包含、可独立测试的模块（库）实现，并具备清晰的单一职责说明；
模块之间只允许通过显式契约通信，禁止为"整理目录结构"而拆分出无独立职责的模块。
新增模块必须自带最小可用测试与用途说明文档，否则视为未完成。

**理由**：自包含模块是可测试、可复用、可替换的前提；职责模糊的"组织性模块"只会增加耦合成本。

### II. 契约先行（显式接口边界）

任何模块对外暴露能力前，必须先定义契约：输入来源（参数 / 标准输入 / 请求体）、
成功输出通道（标准输出 / 响应体）、错误通道（标准错误 / 错误码）。
契约必须同时支持机器可读格式（JSON）与人类可读格式，并在变更时同步更新契约文档与测试用例。

**理由**：先定边界再实现，可以让调用方、测试与文档在同一事实来源上对齐，避免"实现即接口"。

### III. 测试先行（不可协商）

TDD 强制：先写测试 → 确认测试**失败** → 再写实现 → 测试转**通过** → 最后重构。
没有对应测试的实现不得合并；任何缺陷修复必须先补一条能复现该缺陷的失败测试，
修复后该测试转为通过，并回归复查最初症状。

**理由**：测试先行是可验证性的唯一保障；"先实现再补测试"无法证明代码真的满足需求。

### IV. 集成测试覆盖关键接缝

以下场景必须有集成测试（单元测试不足以替代）：新模块契约测试、契约变更、
跨模块 / 跨服务通信、共享数据结构（schema）变更。
集成测试必须运行在真实或等价替身（如真实数据库容器 / 真实 HTTP 调用）之上，禁止用mock掩盖接线错误。

**理由**：缺陷集中在模块接缝处，只有集成测试能覆盖接线、序列化与协议层面的问题。

### V. 可观测性、版本管理与简洁

- **可观测性**：所有服务与模块必须输出结构化日志，关键路径带可关联的请求标识；
  错误必须携带上下文且可被检索。
- **版本管理**：对外接口遵循 MAJOR.MINOR.PATCH；破坏性变更必须提供迁移计划、回滚方案与影响清单，
  并在发布说明中标注。
- **简洁**：默认采用最简单可满足需求的方案（YAGNI）；引入任何额外抽象、依赖或复杂度，
  必须书面说明其解决的问题与被否决的更简单方案。

**理由**：可观测性决定故障能否被定位；版本纪律决定变更能否被安全回滚；简洁决定长期维护成本。

## 附加约束（技术栈与红线）

- **技术栈由方案阶段决定**：功能规范（spec）只描述 what 与 why，MUST NOT 出现具体技术栈、
  框架或库名；技术选型由 `/speckit-plan` 产出并记录在该功能的 `plan.md` 中。
- **依赖引入需论证**：新增第三方依赖必须说明必要性、维护活跃度与替代方案；
  能用标准库解决的 MUST NOT 引入依赖。
- **数据与安全基线**：涉及用户数据的存储与传输必须显式说明加密、脱敏与访问控制策略；
  密钥、口令等敏感信息 MUST NOT 进入代码库或制品。
- **领域合规（未成年人数据）**：本项目主要用户为初中生，MUST 遵守以下条款 ——
  1. **最小必要**：仅收集实现功能所必需的信息（登录名、昵称与口令哈希），MUST NOT 收集邮箱、真实姓名、
     学校、班级、住址、身份证件号等身份信息；
  2. **最小展示**：页面与接口 MUST NOT 展示可定位到线下身份的信息；
  3. **无第三方共享**：用户数据 MUST NOT 共享、出售或同步给任何第三方；
  4. **无行为追踪**：MUST NOT 引入用户行为追踪、广告或个性化推荐类组件；
  5. **数据本地化**：用户数据 MUST 仅存储在自有服务器数据库中；
  6. **新增字段前置审查**：任何涉及收集未成年人信息的字段新增，MUST 先修订本章程并通过合规审查。

## 开发工作流与质量门

- **采用规范驱动开发（SDD）流程**：
  `/speckit-constitution` → `/speckit-specify` → `/speckit-clarify` → `/speckit-plan`
  → `/speckit-checklist` → `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement`
  → `/speckit-converge`。
- **逐步交付、逐步确认**：每个阶段产出制品后 MUST 先人工检查，再进入下一阶段；
  禁止一次性串联执行多个阶段而不检查产出。
- **质量门**：
  1. 阶段产物缺失或自相矛盾 → 不得进入下一阶段；
  2. 测试未全绿 → 不得进入 `/speckit-implement` 的下一任务；
  3. 破坏性变更缺少迁移计划与回滚方案 → 不得实施。
- **收敛标准**：反复执行 `/speckit-implement` 与 `/speckit-converge`，直到收敛报告给出 `Converged`。

## Governance

本章程优先于项目内其他任何实践与惯例；冲突时以本章程为准，并按下列流程修订。

- **修订流程**：任何条款变更 MUST 同步完成三件事 —— 更新版本号（语义化）、
  在文件顶部生成 Sync Impact Report、更新 "Last Amended" 日期。
- **版本策略**：MAJOR = 移除或重新定义既有原则；MINOR = 新增原则或实质性扩充指引；
  PATCH = 措辞澄清、错别字与非语义性修正。
- **合规审查**：每次代码评审与每个阶段产物检查 MUST 核对本章程条款；
  引入复杂度 MUST 提供书面论证；无法自证合规的实现视为未完成。
- **运行时指导**：日常开发以当前功能的技术方案与验证指南为准 ——
  `specs/001-word-study-quiz/plan.md`（技术选型、结构、章程合规）
  与 `specs/001-word-study-quiz/quickstart.md`（端到端验收场景）；
  接口以 `specs/001-word-study-quiz/contracts/api.md` 为唯一契约来源。
